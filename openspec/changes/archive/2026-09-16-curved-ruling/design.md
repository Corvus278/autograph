## Context

Мотивация — `proposal.md` («Why»), требования — дельты в `specs/`.

Что важно знать про текущее устройство:

- разлиновка листа — `SheetRuling` (`lib/paper/paper.types.ts`): `step`, `firstLinePhase` (высота линии у **левого** края кадра по модулю шага), `skewAngle`, `margins`, `marginLineX`, `marginLineSide`. Линия `k` проходит по `y = firstLinePhase + k·step + x·tgθ`. Ширины кадра в разлиновке нет — она у листа;
- её потребители — калибровка (`lib/calibrate/deriveGeometry.ts`: кегль, интервал, отступы), вместимость страницы (`lib/paginate/countPageLines.ts`), отпечаток кэша раскладки (`model/measureLayout.ts:34` перечисляет поля разлиновки поимённо), отражение (`lib/paper/mirrorSheetRuling.ts`), ручная правка (`RulingForm` показывает шаг, фазу и поля, округлённые до сотых, и отдаёт округлённые; `PaperGroup.tsx:121` собирает разлиновку заново из перечисленных полей), разбор JSON (`model/paperSheetJson.ts` только читает), запись своих листов (`model/userSheetsStorage.ts`: индексная запись несёт `ruling` как есть, `JSON.stringify`), сборка профилей (`scripts/build-paper-profiles.ts`: `JSON.stringify(artifact)`);
- детектор (`lib/paper/detectRuling.ts`) уже режет кадр на равные полосы (`buildStripProfiles`, профили вдоль наклонных линий) и уже ищет линию в окне вокруг прямой гребёнки (`locateLineInStrips`, `LINE_SEARCH_SHARE = 1/6`): изгиб горизонтальных линий там гасится медианой по полосам, а не измеряется. Вертикальные границы меряются так:
  - линия поля — по профилю столбцов, усреднённому по всей высоте (`findMarginLine`), то есть по среднему положению;
  - крайние вертикали клетки — самое внутреннее положение по полосам, но в окне ±⅙ шага вокруг прямой гребёнки (`findGridColumns`);
  - концы горизонтальных линий — по отклику гребёнки, усреднённому по всей высоте (`buildCombResponse` → `findSignalRegion`);
- отрисовка (`lib/render/renderPageToCanvas.ts`) ставит текст стеком трансформаций канвы: `scale` → `rotate(blockRotate)` вокруг левого верхнего угла страницы → `translate(leftPadding, topOffset)` → `translate(0, baselineY)`, поворот и сдвиг строки вокруг середины блока → поворот, скос и сдвиг слова вокруг его середины → координаты контура глифа. `blockRotate` равен `ruling.skewAngle` (`model/buildPageRenderParams.ts`). `RenderContext` не умеет `setTransform` и `getTransform`: только `save`/`restore`/`scale`/`translate`/`rotate`/`transform`. Записывающий контекст `tests/helpers/path-recorder.ts` матрицу ведёт и отдаёт путь в пикселях страницы;
- контуров нет у всего пользовательского шрифта и у встроенного, пока он не разобран (`model/useFontGlyphs.ts` отдаёт `null`; `PageGlyphs` в `render.types.ts`). Тогда слово рисуется `fillText` целиком (`drawWordText`), а при побуквенных искажениях — по буквам с шириной из `measureText`. У встроенного шрифта `fillText` достаётся ещё подменённому начертанию буквы и символу, которого нет в шрифте;
- слой чернил после отрисовки проходит шейдер освещения и текстуры (`lib/ink/`); без WebGL чернила рисуются прямо на страницу без модуляции;
- замер на фото пользователя (журнал `sheet-native-ruling`, приёмка 6.5): отход линий от гребёнки до ±8 px (0,17 шага) в центре, до 15 px (0,3 шага) в углах, шаг 47,9 px.

## Goals / Non-Goals

**Goals:**

- изгиб — поправка поверх прямой наклонной разлиновки: все нынешние потребители `step`/`firstLinePhase`/`skewAngle` продолжают работать без изменений;
- попадание базовой линии на линию листа — не хуже одной десятой шага в любой точке строки, включая зеркальную страницу и свой шрифт;
- изгиб существует только там, где измерен надёжно; в остальных случаях лист ровный, как сейчас;
- отрисовка остаётся детерминированной и одинаковой в предпросмотре, экспорте и пачке, с WebGL и без; путь ровного листа не меняется ни в одном вызове контекста.

**Non-Goals:**

- выпрямление фотографии и перспективное преобразование листа — фотография по-прежнему не пересемплируется;
- изгиб вертикальных линий в раскладке: край блока прямой, строки не меняют длину по высоте листа;
- перспективное изменение шага и кегля по высоте листа: кегль и шаг строк у страницы один, неравномерность шага по высоте поглощается смещениями изгиба;
- ручная правка изгиба и переключатель «учитывать изгиб» в интерфейсе;
- досчёт изгиба у ранее сохранённых своих листов;
- изгиб формы букв своего шрифта: без контуров буква садится на линию целиком, но сама не гнётся.

## Decisions

### Изгиб — равномерная сетка смещений поверх прямой гребёнки

`SheetRuling` получает обязательное поле `bend: RulingBend | null`, `SheetRulingSource` — необязательное `bend?: RulingBend | null`: при `exactOptionalPropertyTypes` иначе нельзя передать спредом `null` из детекции. Обязательное, а не необязательное: забытый перенос изгиба — ровно та ошибка, которую иначе не видно (сборка разлиновки в `PaperGroup`, отражение), и компилятор должен её ловить.

Сетка несёт собственную меру, поэтому выборке не нужны ни ширина кадра, ни шаг:

```ts
type RulingBend = {
  columnOrigin: number;  // x первого узла, px
  columnSpacing: number; // расстояние между узлами по x, px
  columnCount: number;
  rowOrigin: number;     // координата вдоль линий u первой строки узлов, px
  rowSpacing: number;    // расстояние между строками узлов — шаг гребёнки при измерении, px
  rowCount: number;
  offsets: number[];     // смещения линий по вертикали, px, до сотых; построчно, rowCount × columnCount
};
```

Узлы по x стоят в центрах равных полос, нарезанных по горизонтальной области с линиями — от левой границы `left` до правой `right` (см. «Измерение»). Поэтому `columnOrigin = left + columnSpacing / 2`, `columnSpacing = (right − left) / N`, и сетка равномерная. Отдельных узлов на краях области и кадра нет. Строки узлов — подряд идущие линии гребёнки внутри области с линиями.

Координата вдоль линий `u = y − x·tgθ` — высота у левого края кадра той прямой наклонной линии, что проходит через точку. Смещение в точке `(x, y)`:

- по `x` — равномерный кубический Катмулл — Ром по узлам строки: гладкая производная нужна повороту букв без контура и не даёт изломов строки на узлах. Фантомные узлы за краями зеркалят соседний (`P₋₁ = P₁`, `P_N = P_{N−2}`): касательная в крайнем узле нулевая, и стыковка с константой за ним гладкая — без этого производная на крайнем узле скакала бы от `(P₁ − P₀)/2` к нулю;
- между строками узлов — линейно по `u`: базовые линии садятся ровно на линии, а между ними смещение нужно только телу букв. Излом производной по `y` на каждой линии тело буквы пересекает не больше одного-двух раз, и на глаз он не виден;
- за пределами сетки — значение ближайшего узла (константа). Это полполосы у краёв области с линиями (около шага) и всё, что за областью, — поле, спираль, край кадра, — а также зона над верхней и под нижней найденной линией.

Реальное положение линии `k`: `y_k(x) = firstLinePhase + k·step + x·tgθ + d(x, u_k)`.

Выборка — чистая функция `sampleRulingBend(bend, skewAngle, x, y)` в `lib/paper/`. У неё есть и производная `∂d/∂x` при постоянной `u` — вдоль линии, а не при постоянной `y`: поворот буквы без контура должен добавить к наклону разлиновки ровно кривизну линии, а производная при постоянной `y` отличалась бы на `tgθ·∂d/∂u`. Её зовут отрисовка и тесты.

Инвариант: без шага нет и изгиба. `buildSheetRuling` при `step ≤ 0` отдаёт `bend: null` — чистый лист и ручной ввод без шага не несут сетку, относящуюся к несуществующей гребёнке.

Почему сетка, а не полином:

- **двумерный полином** (кубика по x × квадратика по y) описывает перспективу, но не местную волну бумаги у спирали и звенит в углах — ровно там, где изгиб наибольший;
- **полином на каждую линию** не видит волну и требует отдельной подгонки на каждой из 40 линий с худшей устойчивостью у коротких линий;
- **растровая карта смещений** рядом с картой текстуры — лишний файл и лишняя загрузка ради сотен чисел.

Сетка честно хранит измеренное, интерполяция за O(1), а объём мал: 40 линий × 16 узлов — 640 чисел; при сотых пикселя — около 4 КБ на лист.

Почему поправка, а не замена модели на ломаные линий: калибровка, вместимость, отражение полей, форма правки и отпечаток кэша считаются от шага и фазы. Замена модели переписала бы их все ради того, что влияет только на отрисовку.

### Изгиб не влияет на раскладку

Кегль, интервал, отступы, вместимость и переносы считаются по прямой гребёнке, как сейчас (spec `page-calibration`: «Строки повторяют изгиб разлиновки», «Страница заполняется до нижнего поля своего листа»). Изгиб сдвигает уже разложенные строки только при отрисовке.

Следствия:

- отпечаток кэша раскладки (`measureLayout.ts`) изгиб не включает: он перечисляет поля разлиновки поимённо, и `bend` туда не добавляется;
- базовая линия последней строки на отрисованной странице может уйти ниже нижнего поля на величину изгиба, не больше половины шага (см. проверку надёжности). Это тот же класс сдвига, что даёт наклон: у `grid-1` он достигает 33 px вдоль строки. Найденное нижнее поле бывает уже фолбэка в полтора шага, поэтому низ строчного бокса последней строки в кадре проверяет story `TextStaysOnPaper` (см. риски).

Альтернатива «учитывать минимум изгиба первой строки в верхнем отступе» отвергнута: калибровка стала бы зависеть от изгиба, и переимпорт листа с чуть другим изгибом менял бы число строк на странице.

### Измерение: трассировка линий от центра к краям

Новый модуль `lib/paper/detectRulingBend.ts`. Он вызывается из `detectRuling` после того, как найдены шаг, фаза, наклон, область с линиями и её боковые границы (концы линий, линия поля), а результат кладётся в `RulingDetection.bend` — обязательное поле типа из `paper.types.ts`, а не расширения `DetectedRuling`: через `RulingDetection` изгиб типизированно доезжает и до `SheetMeasurement.detection` в импорте. Неудача детекции (`toMissingDetection`) отдаёт `null`. Оба вызывающих — `useSheetImport` и `build-paper-profiles` — получают изгиб без изменения порядка вызовов: разлиновку строит `buildSheetRuling({ ...detection })`.

Шаги:

1. **Полосы.** Режется не весь кадр, а горизонтальная область с линиями: от одного конца линий до другого, со стороны линии поля — до неё. Полос `N = max(8, round((right − left) / (2·step)))`, они равные, вертикальные, по оси `horizontal` с углом наклона (`buildStripProfiles` на вырезке области). Верхнего предела у `N` нет: потолок при мелком шаге и широком кадре раздвинул бы узлы шире двух шагов и поднял нижний предел волны. За пределами области узлов нет. У спирали, на столе и за линией поля, где у пресетов клетки идёт мелкая линейка со своим шагом, трасса цеплялась бы за чужие провалы, срабатывала бы проверка скачков, и изгиб молча отбрасывался бы целиком. Внутри полосы в два шага линия почти прямая: при изгибе в 15 px на полкадра полоса в 100 px добавляет ~2 px размытия. Профили очищаются от фона (`detrendProfile`). Узлы через два шага и полосы шириной в два шага разрешают волны бумаги не короче 8 шагов: полоса ослабляет волну длиной `λ` в `sinc(2π/λ)` раз — при 8 шагах до 0,90, а волна в 4 шага — уже до 0,64 и лежит на пределе частоты узлов. Более короткая волна на тетрадном листе — складка, а не изгиб, и попадание на ней не гарантируется: это ограничение, а не цель.
2. **Старт.** Каждая линия гребёнки внутри области с линиями ищется в окне ±⅓ шага. Поиск идёт с центральной полосы, а если там линии нет (пятно, текст), — со следующей ближайшей к центру, где она нашлась. Окно шире `LINE_SEARCH_SHARE`: в центре отход доходит до 0,17 шага. При этом оно уже половины шага и соседнюю линию не достаёт. Положение узла — вершина провала, уточнённая параболой (`refinePeakOffset`). Если плечи провала на полуглубине расходятся от вершины несимметрично — на два бина профиля и больше, — берётся центр тяжести части провала глубже половины вершины (`locateDipCenter`): у линии, изогнутой внутри полосы, самый тёмный бин уезжает к её плоской части, и ошибка восстановления росла до 0,07 шага при 0,03 у точного замера на той же сетке. Центр тяжести на любом провале отвергнут: на симметричном провале он шумнее вершины и ухудшал уже точные случаи.
3. **Трассировка.** От стартовой полосы к левому и правому краю. Предсказание в следующей полосе — положение в предыдущей плюс наклон по двум последним. Поиск идёт в окне ±⅙ шага вокруг предсказания, а если там линии нет — в запасном окне ±⅓ шага: на склоне прогиба предсказание по двум последним узлам отстаёт от линии, узлы терялись и заполнялись константой. Узлы, найденные в окне ⅙, от запасного окна не меняются. Линия мельче 0,1 типичной глубины линий (`LINE_DEPTH_LEVEL`) даёт пропуск: предсказание продолжается, узел помечается ненайденным. Порог в пятую часть глубины терял крайний столбец узлов: на крупном кадре линия, изогнутая внутри полосы, размазана, и у края области, срезанного наклоном, её провал мельче. Трассировка, а не независимый поиск в каждой полосе: к краю отход растёт до 0,3 шага, и окно вокруг прямой гребёнки там цепляло бы соседнюю линию.
4. **Фильтр выбросов.** Узел заменяется медианой соседних линий в том же столбце (3×1), только если отличается от неё больше чем на ⅒ шага. У первой и последней строки узлов медиана берётся по трём ближайшим строкам внутрь области (`r`, `r ± 1`, `r ± 2`). Медиана из двух значений в `computeQuantile` равна большему из них, и выброс вверх у крайней строки остался бы. Так снимаются одиночные выбросы — соринки, клетки поверх линии поля, текст на листе. По высоте изгиб бумаги на три соседние линии почти постоянен, а по ширине волна длиной 8 шагов занимает четыре узла. Медиана по соседним столбцам срезала бы её гребень: при узле на гребне `median(1, 0, 0) = 0`, ошибка — вся амплитуда. Ненайденные и заменённые узлы заполняются интерполяцией по строке, а строки почти без узлов — по соседним строкам. Смещения округляются до сотых пикселя здесь же: в памяти, в хранилище и в артефакте лежит одно и то же число, и отдельный сериализатор изгиба не нужен.
5. **Проверка надёжности** (spec `paper-profile`, «Ненадёжный изгиб не искажает текст»). Изгиб не сохраняется (`null`), если:
   - найдено меньше 60 % узлов области с линиями;
   - фильтр заменил больше 20 % найденных узлов: трасса шумная;
   - где-либо `|смещение| ≥ ½ шага`: трасса перескочила на соседнюю линию;
   - соседние строки узлов расходятся больше чем на ¼ шага в одном узле: изгиб бумаги гладкий, а скачок означает, что одна из линий захвачена чужой;
   - наибольший отход линий от прямой меньше 1/20 шага — в узлах и у обоих краёв области (`measureBendDeviation`): лист ровный, изгиб меньше половины допуска попадания и не стоит ни байта хранения, ни пересчёта контуров. У края отход продолжается параболой через три крайних узла строки на полполосы за крайний узел. По одним узлам отбрасывалась дуга во всю ширину под наклоном: узлы не доходили до 1/20 шага, а прямая разлиновка у краёв уходила от линий на 0,057–0,084 шага. Прямая по двум крайним узлам недобирала у края до 0,005 шага. Цена параболы — переоценка на прогибе, выполаживающемся к краям: при настоящем отходе 0,030–0,044 шага она насчитывает 0,053–0,055, и изгиб сохраняется, а строки от этого не хуже. Поэтому spec в полосе от 0,03 до 1/20 шага допускает оба исхода. Проверка `|смещение| ≥ ½ шага` остаётся по узлам: она ловит перескок трассы, а не форму изгиба.

Пороги — стартовые. Их калибруют на синтетике с известным изгибом, на пресет-паке (скрипт печатает найденное) и на фото пользователя.

### Угол наклона: сверка по вертикалям

Свип угла по резкости горизонтальных линий вбирает изгиб: при прогибе, смещённом к одной стороне кадра, он выбирает угол крутой половины линии. На синтетике прогиб в треть шага давал угол до 2° и терял линию поля, а при наклоне листа 1° уводил строки на шаг. Уменьшенная копия кадра, по которой идёт свип, от этого не спасает.

`detectSkewAngle` сверяет угол по линиям со свипом по вертикалям — линии поля, концам линий, линиям клетки. Если угол линий размывает вертикали ниже половины их лучшей резкости (`VERTICAL_SMEAR_RATIO`), он уведён изгибом, и берётся угол вертикалей. Угол ищет сам `detectRuling`, если его не передали: импорт, скрипт профилей и story `RasterRuling` идут одним путём.

Поправка угла по линейному тренду узлов изгиба отвергнута: по одним линиям наклон листа от линейной части прогиба не отличить, и итерации сходились только для одной формы прогиба.

Точность угла spec требует только на ровном повёрнутом листе. У несимметричного прогиба разложение линии на наклон и изгиб неоднозначно, и там приёмка идёт по положению восстановленных линий и полям, а не по углу. Порог 0,5 подобран на синтетике; лист с перспективой, где вертикали наклонены иначе, чем линии, не проверен.

### Отрисовка: смещение добавляется к точкам в локальных координатах

Стек трансформаций канвы не меняется. Рядом с ним рендерер ведёт ту же аффинную матрицу `M` без `scale` — те же `rotate`, `translate`, `transform` в том же порядке, со своим стеком на `save`/`restore`. Точка контура `p` в локальных координатах буквы рисуется как

```
p′ = p + L⁻¹ · (0, d(M·p)),   L — линейная часть M
```

Тогда её образ на странице — `M·p + (0, d)`: ровно сдвиг по вертикали в пикселях страницы. Контрольные точки кривых Безье сдвигаются тем же полем.

Почему так:

- **соединения не рвутся сами собой.** Смещение — функция точки страницы, а стык соседних букв — одна и та же точка страницы, значит, и сдвиг у неё один. Шов, замороженный в `deformGlyphPath`, остаётся швом;
- **неровность почерка ложится поверх изгиба.** Повороты и сдвиги строки и слова уже вошли в `M`, а изгиб добавляется после них — как у человека, который пишет неровно, но по изогнутой линии;
- **сдвиг контрольных точек вместо деления кривых.** Для перспективы и прогиба отклонение сдвинутой кривой от точно изогнутой — сотые доли пикселя. Для местной волны амплитудой 0,1 шага и длиной от 8 шагов — нижнего предела сетки — оценка `⅛·d″·L²` даёт до ~0,01 шага при букве шириной в шаг;
- **параллельная матрица и перевод обратной линейной частью.** Нарисовать путь сразу в пикселях страницы значило бы снять со стека уже применённые `translate`/`rotate` строки и слова. Снять их нечем: в `RenderContext` нет `setTransform`, а `getTransform` нет ни там, ни в записывающих контекстах тестов. Переписывать же стек под режим изгиба — значит менять ленту вызовов. Перевод смещения `L⁻¹` оставляет все вызовы трансформаций на месте; меняются только координаты точек.

Режим включается только при `bend !== null`. Иначе параллельная матрица не ведётся, выборка не вызывается, и лента вызовов ровного листа совпадает с нынешней.

**Буквы без контура в режиме изгиба.** Слово всегда рисуется по буквам, даже без побуквенных искажений: ширины — из `measureText`, как в ветке побуквенных искажений `drawWordText`. Для буквы берётся точка `c` — середина буквы на базовой линии — и её образ `M·c` на странице. Буква рисуется внутри `save`/`restore`: `translate` на `L⁻¹·(0, d)`, затем `rotate` на `atan(∂d/∂x)` вокруг `c`, затем `fillText`. Поворот задан в локальной системе буквы, поэтому при скосе слова угол приближённый; скос неровности почерка — единицы градусов, и ошибка угла ничтожна.

Этот путь не редкий: он достаётся всему своему шрифту и встроенному, пока тот не разобран. Поэтому на нём держится то же попадание ≤ 0,1 шага (spec `page-calibration`, сценарий «Свой шрифт повторяет изгиб»). Целое слово с одним сдвигом отвергнуто: оно остаётся прямым, и на 300 px в углу листа отход меняется на ~6 px (0,11 шага).

Отвергнутые альтернативы для контуров:

- **сдвиг и поворот слова целиком по касательной** — та же прямота длинного слова; посимвольный вариант для контуров рвёт связный почерк на каждом стыке;
- **деформация готового слоя чернил в шейдере** (выборка слоя в `(x, y − d)`). Без WebGL модуляции нет, и изгиб пропал бы вместе с ней, тогда как попадание на линии обязано работать везде. Пересемплирование размывает тонкие штрихи. Записанная лента вызовов контекста изгиба не видела бы, и тесты попадания пришлось бы строить на растре из шейдера.

`RenderGeometry` получает `bend: RulingBend | null`. Наклон для выборки — `blockRotate`: он равен наклону разлиновки страницы (`buildPageRenderParams`), и отдельного `skewAngle` в геометрии нет. Изгиб страницы (на чётной — отражённый) кладёт в параметры `buildPageRenderParams` из той же разлиновки страницы (`getPageCalibration`), что и геометрию. Через границу воркера он идёт как массив чисел — структурное клонирование его переносит.

### Отражение изгиба

Для отражённого кадра точка `(x′, y)` соответствует `(W − x′, y)` исходного. Подстановка в `u = y − x·tgθ` даёт `u = u′ − W·tgθ`, где `u′ = y + x′·tgθ` — координата вдоль линий отражённой разлиновки с углом `−θ`. Значит:

```
rowOrigin′    = rowOrigin + tgθ · width          // тот же сдвиг, что у фазы и полей
columnOrigin′ = width − (columnOrigin + (columnCount − 1) · columnSpacing)
offsets′[r][i] = offsets[r][columnCount − 1 − i]
```

Область с линиями у листа несимметрична (линия поля с одной стороны), поэтому `columnOrigin′` в общем случае отличается от `columnOrigin`: у отражённого листа область лежит зеркально. `mirrorSheetRuling` уже получает `width` и отражает `bend` вместе с остальной разлиновкой. Проверка — как у наклона: не двойным отражением, где слагаемое сокращается, а положением линии, восстановленным по отражённой разлиновке, против линии отражённого синтетического листа.

### Вертикальные границы — трассировка и самое внутреннее положение

Все три боковые границы сейчас меряются по среднему или в узком окне вокруг прямой гребёнки. Линия поля и крайние вертикали клетки прослеживаются по горизонтальным полосам высотой около полутора шагов (не меньше 8 полос на кадр) тем же приёмом, что и линии изгиба. Горизонталь внутри такой полосы почти не меняется по `x`, и её фон снимают скользящая медиана и `detrendProfile`. Концы горизонтальных линий меряются по своим полосам — вдоль линий, см. ниже. Перед выбором итога положения сглаживаются медианой по трём соседним полосам: узкая полоса шумнее. Итог — самое внутреннее положение: для левой границы наибольшее `x`, для правой наименьшее. Полосы, где граница мельче порога, не голосуют: у спирали и у края листа её может не быть. Результат не может выйти наружу от нынешнего измерения.

Полосы узкие, а не 8 штук на кадр: полоса отдаёт среднее положение границы по своей высоте. У параболы с экстремумом у края области крайняя из 8 полос даёт 0,77 амплитуды — недобор до 0,07 шага, больше допуска в пиксель и треть зазора ⅕ шага. В полосе в полтора шага недобор ничтожен.

- **Линия поля.** После поиска по среднему профилю столбцов (`findMarginLine`) старт — в полосе с самым глубоким провалом в окне ±⅓ шага вокруг среднего положения, дальше вверх и вниз в окне ±⅙ шага вокруг положения в соседней полосе. Полосы — по оси `vertical`. На листе в клетку в окно попадают обычные вертикали, поэтому узел принимается только с глубиной не меньше 0,8 глубины линии поля в стартовой полосе. Детектор гарантирует лишь, что линия поля в полтора раза глубже девятой децили вертикалей клетки (`MARGIN_LINE_DEPTH_RATIO`, `MARGIN_LINE_PEER_QUANTILE`), а десятая часть вертикалей глубже этой децили. Порог в ⅔ совпал бы с порогом детектора без запаса, тогда как узкая полоса шумнее профиля во всю высоту. Окно ±⅙ шага вокруг среднего положения, без трассировки, не годится: при параболическом изгибе амплитудой `a` среднее отстоит от самой внутренней точки на `2a/3`, и при `a = 0,3` шага это 0,2 шага — больше окна.
- **Крайние вертикали клетки.** `findGridColumns` уточняет крайнюю линию той же трассировкой по полосам вместо окна ±⅙ вокруг прямой гребёнки.
- **Концы горизонтальных линий** (граница области у линейки и у клетки без вертикалей дальше горизонталей). Граница области берётся в каждой полосе, итог — самый внутренний. Три условия делают полосный отклик честным:
  - **полосы режутся вдоль линий, а не по `y`.** Граница полосы — по координате `u = y − x·tgθ` посередине между линиями (`firstLinePhase + (k + ½)·step`), высота — целое число шагов, не меньше двух. Полоса по `y` на наклонном листе ловит то одну, то две линии вдоль `x`: у `grid-1` наклон сдвигает линию по ширине кадра на 0,6 шага. Отклик тогда падает вдвое, ровно до порога области 0,5, и «самое внутреннее» выбрало бы ложный обрыв. Полоса по `u` держит одно и то же число линий на всей ширине, а изгиб до 0,3 шага границу посередине между линиями не пересекает;
  - **фон вычитается внутри полосы.** Из яркости вычитается среднее бина по полосе, а не среднее кадра, как в `buildCombResponse`. На отрезке в несколько периодов `cos` и `sin` постоянный фон не гасят: модуль интеграла на 1,5 периода — около 0,21 отличия бумаги от среднего, и уже при отличии в 0,06 это сравнивается с сигналом линии. Без вычитания чистое поле за концами линий, спираль, стол и тёмные вертикали клетки дали бы положительный отклик;
  - **голосуют только полосы внутри найденной по высоте области с линиями** (`findRuledSpan`): полоса над разлиновкой или под ней отклика не несёт и дала бы ложный обрыв на всю ширину;
  - **защитная полоса наклона считается по высоте полосы, а не кадра.** `buildCombResponse` зовёт `computeGuardBand(angle, height)` от высоты кадра: при 4000 px и 1,5° это около 105 px, и концы линий у края кадра так не измерить;
  - **обрыв внутрь подтверждается общей децилью.** Порог области в полосе — половина девятой децили её же отклика. Зона пониженного контраста — блик или бледный дальний угол — опускает децили нескольких соседних полос сразу, и медиана по трём полосам её не снимает. На фото пользователя бледные крайние линии уже рвали цепочку линий (журнал `sheet-native-ruling`, F2). Поэтому полоса не голосует, если за обрывом есть участок длиной не меньше шага с откликом не ниже половины девятой децили, общей для всех полос. Участки короче шага — пятна спирали, ступень у края стола — голосу не мешают: с условием «весь отклик за обрывом ниже порога» они выключали бы полосы целиком. Затем положения сглаживаются медианой по трём соседним полосам, и итог не выходит наружу от нынешнего измерения.

  Отклик гребёнки в полосе считается по модулю квадратур `√(C² + S²)`, где `C` и `S` — суммы отклонения яркости от среднего бина по полосе с весами `cos` и `sin` фазы прямой гребёнки. Нынешний `buildCombResponse` берёт одну косинусную сумму. Изгиб её расфазирует: при отходе линии на 0,17 шага вес `cos(2π·0,17) = 0,48` уже ниже порога области `RULING_REGION_LEVEL = 0,5`. В полосе, где линии гнутся сильнее всего, область обрывалась бы раньше конца линий, и самое внутреннее значение выбрало бы именно её. Усреднение по всей высоте это сейчас размывает, а полосы — нет. Модуль квадратур от сдвига фазы не зависит, на ровном листе он совпадает с косинусной суммой с точностью до шума. Демодуляция измеренным изгибом отвергнута: граница зависела бы от надёжности изгиба и при его отказе снова расфазировалась бы. Полосный отклик — новый вариант в `lib/paper/sheetProfile.ts`.

Зазор ⅕ шага (`RULED_EDGE_GAP_SHARE`, `MARGIN_LINE_GAP_SHARE`) отсчитывается от уточнённого положения, как сейчас от среднего.

### Правка, хранение, профили

- **Форма правки.** `PaperGroup` передаёт `bend` в `buildSheetRuling` явно. Изгиб сохраняется, если шаг и фаза из формы равны исходным, округлённым так же, как форма их показала (`Math.round(v·100)/100`); иначе сбрасывается в `null`. Точное сравнение с измеренным шагом (`47,9312` против `47,93` из формы) стирало бы изгиб при правке одних полей. Смещения отсчитаны от прямой гребёнки с прежними шагом и фазой: при другом шаге или фазе те же числа описывали бы отход от других прямых, и строки встали бы мимо линий.
- **Разбор JSON.** `paperSheetJson` читает `bend`. Размеры, не согласованные с длиной `offsets`, неположительные интервалы, нечисловые значения и отсутствующее поле дают `null`: такой лист ровный, а не сломанный. Писать изгиб отдельно не нужно: `userSheetsStorage` кладёт `ruling` в индексную запись как есть, скрипт пишет артефакт `JSON.stringify`, а округление уже сделано при измерении. Индексная запись каждого своего листа растёт на несколько килобайт — рядом с фотографией в data URL это ничтожно.
- **Версия артефакта не поднимается** (`PAPER_PROFILES_VERSION = 2`). Поле необязательное в JSON, запись без него — ровный лист, а поднятая версия заставила бы приложение отбросить весь артефакт при расхождении.
- **Сборка профилей.** `build-paper-profiles` пишет изгиб и печатает по каждому листу наибольший отход в долях шага и долю найденных узлов — по ним сверяются пороги.
- **Старые свои листы** остаются ровными до переимпорта (решение пользователя): при запуске фотографии не разбираются.

## Risks / Trade-offs

- [Трасса захватывает соседнюю линию на сильном изгибе] → окно трассировки ⅙ шага вокруг предсказания, запасное окно ⅓ шага — только когда в окне ⅙ линии нет (на спирали и чужой линейке ложных узлов оно не дало), старт у центра, где отход наименьший, и проверка скачков между соседними строками узлов; при отказе — ровный лист.
- [Текст на фото, спираль, соринки, чужая линейка за линией поля дают ложные узлы] → узлы только внутри горизонтальной области с линиями, фильтр выбросов по соседним линиям, порог доли найденных узлов по узлам области, пропуски вместо захвата мелких провалов; тест со спиралью и линейкой другого шага за линией поля.
- [Трасса линии поля на клетке уходит на обычную вертикаль] → порог глубины 0,8 от стартовой полосы; тест на клетчатом синтетическом листе с изогнутой линией поля между вертикалями.
- [Правка границ сдвигает поля пресетов, найденные в `sheet-native-ruling` (F1/F2)] → после задач границ `build:paper` прогоняется, и поля и линия поля каждого листа сверяются с прежними с допуском в пиксель — по печати скрипта или `jq`. `git diff` бесполезен: артефакт однострочный. Эталон пишется в журнал, а `public/paper` (артефакт и перезаписанные карты текстуры) возвращается `git checkout` до пересборки с изгибом.
- [Бледная зона на части ширины уводит конец линий внутрь] → обрыв в полосе принимается только по общей для всех полос децили, сглаживание по трём полосам, итог не наружу; тест с пятном пониженного контраста на 3–4 полосы.
- [Импорт медленнее: проходы по полосам для изгиба и трёх границ] → профили полос строятся O(пикселей) на проход, трассировка — O(линий × полос × окно). Время `detectRuling` замеряется на синтетике 3000×4000: база — до первой правки детектора, итог — после всех. Если рост заметный — а предыдущий change уже добавил +35 %, — первый рычаг: общий проход по полосам для изгиба, `findRuledSpan` и границ.
- [Пределы раскладки узлов] → узлы стоят только внутри области с линиями и не чаще двух шагов, за крайним узлом смещение постоянное. Поэтому даже при точном замере узлов у края области, срезанного наклоном, ошибка восстановления доходит до ~0,15 шага, дуга в треть шага при наклоне 0,5–2° — до 0,08, волна короче 8 шагов — 0,05. Ограничение принято (spec `paper-profile`, «Линии изогнуты»); узлы до края кадра и продолжение изгиба за крайний узел — после приёмки на фото пользователя.
- [Свой шрифт рисуется по буквам и теряет контекстные лигатуры и кернинг внутри слова] → только в режиме изгиба; тот же компромисс уже принят в ветке побуквенных искажений. Ширина слова по сумме букв расходится с шириной, по которой резались строки, на величину кернинга — единицы пикселей на слово; последнее слово строки может выступить за край блока на столько же. Это ловит вариант story `TextStaysOnPaper` без контуров: шрифт пака регистрируется под пользовательским именем, контуров у него нет, свес буквы берётся из `measureText`.
- [Верх бокса первой строки или низ бокса последней уходят за кадр вслед за изгибом] → раскладка от изгиба не зависит; story `TextStaysOnPaper` прогоняется на пресетах с изгибом и проверяет оба края. Если на пресете бокс выйдет за кадр, это конфликт со spec `page-render` («Текст остаётся на бумаге»), и он поднимается пользователю, а не чинится молча калибровкой.
- [Пресеты получат изгиб, и эталоны скриншотов поедут] → переснять в docker-образе (`npm run test:visual:update`), сверив диф глазами: сдвиг строк вдоль линий, а не перекладка.
- [Stories попадания считают линию прямой] → арифметика `BaselineFit` и растровый замер `RasterRuling` переводятся на положение линии с изгибом в нескольких точках строки, с отрицательным контролем на том же листе без изгиба: иначе они либо упадут на пресетах с изгибом, либо ничего не проверят.

Растровый замер идёт на изогнутом листе, сгенерированном прямо в файле story: хелперы `tests/` из `src` недоступны.
- **Изгиб листа.** Его находит `detectRuling` на растре этого листа. Изгиб зависит только от `x` и несимметричен: при симметричном отражённый и неотражённый изгиб совпадают, и зеркальная страница ничего не проверяет. Страница проверяется в нечётном и зеркальном варианте. Перед замером story числом проверяет, что найденный изгиб в центрах крайних полос не меньше 0,25 шага. Детектор снимает с изгиба среднее (фазу), а свип угла может забрать в наклон его линейную часть: парабола в 0,3 шага к краям оставляет в полосе на три шага внутрь лишь около 0,14 шага — ниже допуска чернил 0,15, — и отрицательный контроль ничего бы не различил. Форма изгиба подбирается под это условие.
- **Замер.** Два замера в каждой узкой полосе по `x`, не шире трёх шагов:
  - **базовые линии против линий растра под 0,1 шага.** Базовая линия — из геометрии (`buildBaselines`) плюс `sampleRulingBend` найденного изгиба в центре полосы, линия — с растра фотографии. Проверка не сравнивает изгиб сам с собой и держит сквозной допуск спек 0,1;
  - **низ чернил строки против линии растра под допуском чернил story.** Только этот замер видит изгиб в отрисовке: базовые линии геометрии от него не зависят. Поэтому на нём стоит отрицательный контроль — `bend: null`, а на зеркальной странице ещё и неотражённый изгиб листа, — и прогон варианта без контуров (сценарий «Свой шрифт повторяет изгиб»). В каждой полосе должны быть чернила каждой строки: полоса, попавшая между словами, прошла бы вхолостую, потому что `measureInkOffset` строку без чернил пропускает.
- **Пресеты.** Их проверки (`expectRasterOnRuling`, `checkFamily`) переходят на тот же замер по полосам.
- **`TextStaysOnPaper`.** Оба варианта — с контурами и без — гоняются и на этом листе с проверкой `params.geometry.bend !== null`: у пресетов изгиба может не оказаться, и путь по буквам без него не исполнится.

Если на пресетах изгиб не превышает допуска, отрицательный контроль `BaselineFit` делается на самом изогнутом пресете с изгибом, растянутым до 0,4 шага (story `BentRulingOnSheet`, только арифметика). Отражение изгиба эта арифметика не видит — изгиб отрисовки и разлиновки берутся из одной отражённой разлиновки, — и его, как и сквозное попадание, держит растровый замер.

## Migration Plan

1. Модель, выборка, отражение: `RulingBend`, `sampleRulingBend`, `bend` во всех литералах разлиновки — везде `null`.
2. Синтетический лист с изгибом и изогнутыми границами; измерение изгиба, проверка надёжности, трассировка трёх боковых границ; вызов из `detectRuling`.
3. Разбор JSON, импорт, форма правки, сборка профилей; пересборка `profiles.json` со сверкой напечатанного.
4. Отрисовка: параллельная матрица, смещение контуров, побуквенный путь без контуров, параметры отрисовки.
5. Stories, эталоны, документация, приёмка на фото пользователя.

Откат по данным не нужен: без изгиба лист ровный, и артефакт старой сборки читается новым кодом как есть.
